# Staged restore executor

`python tools/fleet/restore-staged.py PRIVATE_CONFIG_JSON` now performs a real MySQL restore into a separately provisioned empty recovery database. It does not provision accounts, activate billing, replace `.env`, or delete a surviving database. Configuration stays outside Git with owner-only filesystem access.

Required configuration: `database` (pattern `badizo_recovery_` followed by 8–32 lowercase letters/digits), `host` (loopback), `user`, `password`, `shopId`, `artifactDirectory`. Optional `mysqlPath` selects the installed MySQL client; `sourceDatabase` defaults to `badizo_pos`. The artifact directory contains the SQL file and manifest prepared by recoveryBackupArtifact.

The account must have no roles, no global privileges except USAGE and no grant option. Grant privileges only on the exact recovery database; escape underscores in the MySQL grant pattern so they cannot act as wildcards. Supply the needed restore privileges (SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, ALTER, INDEX, REFERENCES, LOCK TABLES). Broader accounts fail preflight. The executor requires MySQL 8.0 and an empty target.

The executor verifies the SQL checksum again, handles the declared mysqldump CREATE DATABASE/USE header, restores with local file imports disabled, checks required tables, runs CHECK TABLE QUICK, and records product/invoice counts. A failure leaves the partial recovery database for inspection and does not grant activation. Restarting against a nonempty partial database is deliberately rejected; provision a new empty recovery database.

The result states `stagedRestoreVerified=true`, `businessReconciliationVerified=false`, `activated=false`. Table integrity is not complete business reconciliation, source-shop attestation or printer validation. Installation still needs a trusted backup source manifest and an activation workflow preserving local credentials/printer settings.

The real HFM backup contains `products_previous_update_timestamp`, a root-defined trigger. Cloud MySQL has binary logging enabled and trusted function creators disabled. The initial restricted restore correctly failed. The executor now recognizes only the exact reviewed trigger body and requires an explicitly supplied trusted installation adapter. It removes that exact declaration from the restricted import and asks the adapter to install the version-controlled trigger against the validated recovery database. The adapter never receives executable SQL from the backup. Unknown or altered stored objects fail preflight. No global MySQL setting is changed and the data import user does not receive global privileges.

On 2026-11-02 the complete confirmed HFM backup successfully restored into isolated `badizo_recovery_20261102b`: 50 tables, 76,384 products and 72,656 invoices. All table checks passed. Trigger metadata matched the reviewed definition, and a transactional product update verified previous_updated_at behavior before rollback. The production cloud service remained active. This validates Linux/MySQL 8.0 staged restore, not Windows activation, business reconciliation or full emergency readiness. The trusted adapter used for this drill was an operator-run script; production adapter provisioning and the button workflow are still pending.

Do not run concurrent restores into the same target. Target-level job locking and a managed provisioning API remain required before wiring this CLI to a user button.

## Opt-in job and screen integration

The new `/api/staged-restore` routes are mounted only with `BADIZO_STAGED_RESTORE_ENABLED=true`. Required deployment settings are `BADIZO_SHOP_ID`, absolute protected `BADIZO_RESTORE_CONFIG`, and private `BADIZO_RESTORE_JOB_DIR`; `BADIZO_PYTHON` selects the Python executable. Build the optional System panel with `REACT_APP_STAGED_RESTORE_ENABLED=true`. SERVER users can confirm a staged restore and inspect its persistent job status. Browsers cannot supply database paths, passwords, SQL or target names. No activation endpoint exists.

The job service serializes work through an exclusive lock in its configured job directory. All workers for a target must share that directory. Failed jobs retain the lock for inspection; process interruption is never retried automatically because a MySQL child may still be importing. Successful reports survive reopening the panel. A stale running status requires operator inspection. The service must run under an OS account with private access to the configuration and job directory.

The Python CLI accepts an optional `triggerInstallerDefaultsFile` only in its installer-owned private configuration. This must be an absolute path to a separately protected MySQL client credentials file for the local privileged installer account. It is used only for the version-controlled reviewed trigger SQL against the validated recovery target, never for the dump import. Linux rejects group/world-accessible credentials; Windows deployment must enforce owner/service-only NTFS ACLs. Without this configuration, trigger-bearing backups fail before import. The successful Linux drill exercised the same trusted SQL through an explicit adapter; the configured CLI adapter and browser button still need an end-to-end deployment drill. The new screen is not enabled on any deployed server.

An additional owner-API integration drill passed on 2026-11-02 using `validate-restore-api.cjs`, the real job service, the configured Python CLI adapter and a fresh `badizo_recovery_20261102c` database. It restored 50 tables, 76,384 products and 72,656 invoices. Unauthenticated/counter/admin access, client-supplied configuration paths and concurrent job submissions were rejected. The verified result survived reopening the job store. The privileged installer credentials stayed in a root-only file. This is real API-to-MySQL validation; browser clicks, Windows behavior and billing activation remain unverified. The validation CLI resolves Express/JWT from the backend installation via NODE_PATH when run outside its directory.

The executor uses a private temporary credential file, with Windows ACL restriction before writing credentials and mode 0700/0600 on Linux. Passwords are not passed in command arguments. This script is not connected to a public HTTP endpoint or deployed as a shop button yet. Windows acceptance testing and abrupt interruption tests remain required.
